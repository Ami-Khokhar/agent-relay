# Decisions

## `?tag=` is a repeatable all-match filter, and `model`/`tags` stay listing-only metadata

Callers need to pick a worker by data instead of matching `name` prose, so `GET /v1/agents`
reports `model` and `tags` when the registry declares them and keeps only the agents carrying
every `?tag=` the query names. All-match is the contract: with `tag=reviewer&tag=factory` an
agent tagged only `reviewer` is absent, while an unknown or blank tag is a tag no agent
carries, so the filter yields an empty list rather than a 400 — a stale label is a fact about
the registry, not a malformed request, and callers treat an empty list as "none available".
Neither field is read by any execution path; they are discovery metadata only, each validated
as a non-blank string and stored trimmed, so the listed value is the value that was validated.
Consequence: a change to any-match, to rejecting an unknown tag, or to letting an execution
path read `model` or `tags` contradicts a public contract and must supersede this decision
rather than edit it, and the trimming is pinned because a stored untrimmed value would list
something no validation accepted.

## A failed foreach step keeps its JSON array output

`_reap` stored the first failing task's scalar output in a failed `foreach` step, while a successful one stored `json.dumps(outputs)`, so the documented array shape broke exactly on the run a caller was inspecting. A `foreach` step whose tasks ran now serializes every item's output in that attempt's order whatever the outcome — the failed item as its own output, empty when it produced none; a step that fails before its tasks run (unresolved template, rejected submission, evicted task) still has no output. Non-foreach steps keep their scalar output, and `taskIds` lists each attempt's tasks in foreach order, oldest first, so a position maps to an item only within one attempt. Consequence: the shape no longer depends on the outcome of the tasks that did run, and no field is added to the payload.

## prepare-activation proves the checkout against the stage receipt's source commit

`prepare-activation` compared the active checkout's HEAD with the approved
release's target commit and refused otherwise, so the real public flow could
never pass its own activation: `activate` requires the checkout at the
transaction's starting revision — the running relay's commit, which equals the
checkout the relay was started from — while the target commit exists only in
the private stage until the swap. The checkout proof now compares against the
stage receipt's bound `sourceCommit` (and its `sourceRoot`), which is exactly
what "changed since staging" means, while release drift stays covered by the
identity-digest comparison. Consequence: an update flows approve → stage →
prepare → activate with the checkout at the old revision throughout, and a
checkout mutated between staging and preparation is still refused before any
drain effect. The integrated acceptance suite
(`test/test_safe_update_acceptance.py`) fails without this fix.

## Temperature configuration errors stay visible and tests isolate owner probes

A configured but unusable temperature reader reports a setting-specific temperatureReason;
it is never run via PATH or described as an absent sensor. The optional Celsius warning
threshold is validated as finite before the relay starts and by the shared snapshot reader,
so a typo cannot silently disable its warning. Installed services need these settings in
their own unit/plist environment. Test relay fixtures strip inherited reader/threshold
settings before applying explicit test overrides; pressure tests also isolate in-process
settings, so the suite cannot accidentally run an owner's real temperature probe.

## The example network option declares only its enabling value

The Codex example's default args keep its socket restriction; selecting `network: on` adds
the owner's explicit network grant. The example therefore declares only `on`: callers
omit the option for the default rather than selecting an unused empty-args `off` value.
The README and adapter recipe show that same declaration. This changes the example only;
owner registries may still declare other values, including values that map to no args.

## Quota labels require task-error diagnostics and contextual HTTP status codes

This supersedes the output-tail classification fallback in the workflow-cause decision below.
Failed tasks already carry a task error, including a relay-generated message when command
stderr is empty. Classification therefore uses that error only; stdout-only limit text
stays visible in the cause and output without setting the quota label. Numeric 429 reports
need HTTP, status, error or code context, so source line numbers cannot relabel failures.
The existing explicit limit phrases and failed-step ordering remain unchanged.

## Workflow causes prioritize failed steps and diagnostic limit reports

Forward dependencies can put a skipped dependent before the step that actually failed.
The run therefore names the first failed step in document order, falling back to a skipped
step only when no step failed. Quota classification uses explicit limit-report phrasing in
the task error before its displayed tail is shortened, so a traceback cannot hide the report.
Only an empty error permits classification from the output tail; ordinary quota prose does
not label an unrelated failure. Displayed causes remain bounded, and errorDetail retains
the full task error rather than promising stderr for every adapter and failure mode.

## Pressure admission aliases share validation and cause-neutral refusal advice

The admission threshold accepts the first nonempty `AGENT_RELAY_ADMIT_BELOW` or
`A2A_RELAY_ADMIT_BELOW`, matching adjacent pressure settings. Startup validates the selected
value and names that variable on error; each pressure snapshot still reads the setting.
A refusal with readings asks the owner to address those readings and retry, since swap and
temperature warnings are not necessarily fixed by freeing memory. A calm host refused by
an `ok` threshold instead names the setting. Verdict thresholds and active-run stops are
unchanged.

## Release discovery is metadata-only

The project has no published releases or tags yet, and its existing updater pulls and restarts source checkouts. Release discovery therefore uses the canonical GitHub HTTPS API with a bounded response and never installs or executes fetched content. Stable releases are the default, prereleases require an explicit option, and no release is a normal result. Later installation work must establish immutable content verification and a separate user consent step.

## Scheduled checks only offer release metadata

The timer may fetch bounded canonical release metadata, but it must not update installed code or restart the relay. It writes a private, validated offer without marking it offered; MCP initialization reads only that local cache and offers a version notice to the client once per version, while release notes remain available only from an explicit `check_updates` call. This records delivery to the client, not proof that a human read it. The updater script stays a separate manual source-checkout operation until an activation and consent design is ready. Owners must rerun the installer to replace timer definitions installed by an older version.

## The release notice cache serializes whole transactions behind a private sibling lock

The device-local notice cache has two writers — the scheduled timer's refresh and MCP initialization's `cached_notice` — and each one is a read/decision/write sequence: read the cache, decide whether this version was already delivered, write the outcome. Unserialized, two concurrent clients can both decide a version is undelivered and both deliver it, and a timer refresh replacing the file between a client's read and write can erase delivery history and redeliver the same version. The cache file itself cannot carry the lock, because every write atomically replaces it and a lock on the old inode would not follow the replacement. Every transaction therefore runs under an exclusive `flock` on a stable sibling file (`release-notices.lock`), with the same private regular-file checks as the cache (no symlink, owned by this user, mode 0600 on POSIX) applied to the opened lock descriptor rather than its path, so a name swapped after `open` cannot slip an unvalidated file past them; nested entry — the write inside `cached_notice`'s own transaction — reuses the held lock instead of re-acquiring, so a transaction cannot deadlock itself. Lock acquisition is bounded by a timeout, and a failure raises an actionable error: a caller never claims a notice was delivered when the transaction could not run. `_write_cache` without an explicit `notified_version` preserves the previous `notifiedVersion`, and both `cached_notice` and `_notify_once` deduplicate on that one field, so a refresh updates the offer without redelivering a version already shown. A separate consequence of round-tripping offers through the cache: the read cap must cover the worst-case JSON escaping of a maximum-size offer (2000 astral characters serialize as up to 12 characters each, with version strings bounded to 256 characters in both discovery and cache validation), so the cap is 32 KiB rather than 16 KiB, still a bound. On non-POSIX platforms there is no `flock`: the policy is explicit — transactions are not cross-process serialized there, writes stay atomic-by-replacement, and the project's supported notice-cache platforms are POSIX.

## Non-POSIX notice caches retain atomic writes without transaction serialization

This supersedes the POSIX-only support claim in the sibling-lock decision above. The cache
continues to work on non-POSIX systems using user-cache defaults and atomic replacement,
but only POSIX transactions use the cross-process lock, so concurrent non-POSIX clients
can deliver duplicate notices. README and DESIGN describe that limitation rather than
promising cross-process deduplication everywhere. The 256-character version bound applies
to discovered tags, cached offers and the stable tags resolved by release_identity before
any HTTP request. For cached offers, the version bound together with bounded notes keeps
legitimate offers within the 32 KiB read cap.

## Truncated release notes say so instead of ending mid-sentence

A release body longer than the 2000-character notes bound is stored as an excerpt, but nothing distinguished that excerpt from a complete body: the CLI printed it as "Release notes" and `check_updates` returned it as `releaseNotes`. `discover()` now records `notesTruncated` in the offer (true when the cleaned body exceeded the bound), the private cache validates and keeps that flag (an absent flag reads as false, so offers written before it remain valid), the CLI prints the bound and the canonical release URL when it is set, and `check_updates` returns `releaseNotesTruncated` beside the notes. Consequence: every reader can tell an excerpt from the whole body and send the person to the release URL for the rest; the notes stay bounded untrusted data.

## A foreach step matches fail patterns per item

`failIfOutputMatches` used to be tested against the step's aggregated output, which for a `foreach` step is a JSON array of the item outputs. An anchored pattern then either could not see what an agent reported (`^BLOCKED` never matches a report quoted inside the array) or fired on the serialization itself (`^\[` failed every healthy fan-out). The pattern is now tested against each completed task's own raw output, before the step may complete: one matching item fails the whole step with `output_matched_fail_pattern` and its dependents are skipped, and the step still keeps the JSON array as its output for a caller to inspect. Consequence: matching is per item, so an aggregate-shaped pattern (`^\[`) no longer has a meaning on a `foreach` step, while the other terminal causes keep their precedence — a task that failed, timed out or was cancelled still decides the step before the pattern is read, and `retries`, `repeat` and journals written before the field existed behave exactly as before.

## Tests never read or consume the device notice cache

MCP initialization reads the device-local notice cache and marks a delivered version, so any test that starts an MCP server process — or calls an in-process initialize handler — against the real environment would consume and rewrite the developer's own notice state, and its assertions would depend on whatever cache and installed version the machine happens to have. Every test MCP process therefore gets a private `XDG_CACHE_HOME`: `McpClient` defaults to a temporary cache it removes in `close()` (a caller-supplied cache is honored and left to the caller), in-process initialize handlers run under a fixture that points `XDG_CACHE_HOME` at a temporary directory, and any other direct `mcp_server.py` spawn must do the same. Tests that seed a notice cache derive the offered version relative to the installed baseline, and scheduled-refresh coverage passes an explicit installed baseline to `cache_latest_offer`, so a version bump in `pyproject.toml` cannot silently invalidate them. Consequence: a new test that spawns the MCP server without a private cache is a regression, and release-offer fixtures must outrank the declared version rather than assume one.

## The release-check timer's units carry no relay environment

`A2A_RELAY_PORT` and `AGENT_RELAY_DIR` used to be set in the update timer's launchd and systemd units alongside the checker's own `ExecStart`. The check is metadata-only: `release_discovery.py --cache-offer` locates the checkout from itself, reads its state from the private device cache, and never talks to the relay, so those variables described a coupling that did not exist; a future reader could also mistake the timer for one that manages the service. The checker units now set only `PATH`, while the relay service's units keep the port and the working directory as before, and the installer's messages and README quickstart describe the timer as a release check. Consequence: the timer keeps its historical unit names (`agent-relay-update.*`, `com.agent-relay.update`) and flags, the relay's configuration is untouched, and tests parse the generated plist with `plistlib` and the systemd sections rather than matching strings, so the environment split is asserted structurally on both service managers.

## Release identity is resolved from canonical tag refs and consent is a private device-local record

The stable-update work needs more than discovery's "a newer version exists": the exact release an operator considers installing must be bound to an immutable commit before any content is trusted. `release_identity.resolve_release` therefore ignores `target_commitish` — which moves and is never proof — and resolves the tag through the bounded canonical `git/ref/tags` API, peeling an annotated tag once through `git/tags`, to a 40-hex commit. Only `Ami-Khokhar/agent-relay` counts, only stable published releases, HTML URL must be canonical, and every strict-JSON parse rejects duplicate keys; absent assets or no release at all are clear refusals, and nothing is ever created on the operator's behalf. The release publishes an `agent-relay-manifest.json` asset (`agent-relay.update/v1`) whose exact fetched bytes are hashed into the identity and whose inventory of tracked path/mode/SHA256 entries is validated strictly; the hash authenticates content only because canonical GitHub maintainers publish it over HTTPS — it is not independent signing, and no signing scheme is claimed.

Approval is its own step and never degenerates into a yes flag or an environment variable: `approve` requires a real TTY and the operator typing the exact version and the full commit, then records under a cross-process lock a private 0600 consent bound to the canonical installation realpath, a locally generated device id, the full identity digest, a fresh nonce, and at most a 15-minute expiry. `consume_consent` re-checks everything — expired, future, replayed, mutated, wrong-device and changed-path consent are all refused — and burns the record atomically. Discovery, scheduled notices and `inspect` remain metadata-only, and the safe-update CLI runs no install and no service control; its `stage` and `drain` steps do run read-only git verification (`inspect_checkout`, `verify_stage`) of the checkout and the staged tree, and the activation that will consume the consent is deliberately left for later stages of the same CLI.

## The update drain is a server-held shared lock with an opaque, transaction-bound capability

Activating a staged release must not race new admissions: an updater that quiesces by reading `/healthz` can still restart in the same instant a task is accepted. The relay therefore holds the quiescence state itself. `POST /v1/admin/update/drain` acquires it once for one transaction, bound to the exact commit the relay reports (`healthz` `revision.commit`, refused when unknown), and returns an opaque 64-hex capability the relay minted; the refusals that close admission (`GET` status composes the verdict from the same counts) are the server's, never the client's. A held drain refuses every new external admission — tasks, workflow submissions and resumes — under the server lock, so a submission and an acquire are one atomic decision, and a replayed `requestId` keeps its prior answer instead of a refusal; already accepted workflows keep reaching their child tasks only through a module-level internal admission path bound to the engine at startup, never through a caller-set request field. Quiescence counts active adapter slots (including cancelled adapters still running), queued accepted tasks, and every nonterminal workflow once — a run in a step gap, a retry delay or awaiting fanout is still work that may create tasks. `GET` status answers only the holder's exact transaction, revision and capability (constant-time compared); malformed fields, wrong revisions, foreign capabilities and even a free drain are errors, never `idle`, and status never hands out a new token. There is no expiry during activation: admission reopens through the explicit `DELETE` release with the same capability (or the durable recovery path below). `safe_update.py drain` is the rehearsal consumer: it verifies the staged receipt and the consumed approval consent, holds the drain, waits a bounded time for the server's own quiescence acknowledgement, prints the result and releases; it calls no service control. A held drain lives only in server memory, so the durable stage pairs it with a persistent barrier (next decision) that survives restarts.

## The activation transaction is a durable journal and a restart-surviving admission barrier

A mid-activation crash must never silently reopen admission or lose the transaction, so `update_transaction.py` keeps one activation transaction per install in a private, no-follow, atomic, fsynced journal (`<state dir>/update/transaction.json`) guarded by a cross-process `flock`, paired with an admission barrier file the relay reads once at startup, before serving work. `begin_transaction` records the exact old relay commit, the target release identity digest, the stage receipt and inventory, hashed references (with digests, never contents or secrets) to the external state the update relies on, and the drain ownership (the opaque capability, never the relay token). `transition` is the only phase change: a compare-and-swap that refuses a replay, a skipped phase and any phase without a consumer in the issue that introduces it. The relay's admission gate checks the live drain and this barrier together; a journal or barrier that is unreadable, torn, stale (outliving its record), bound to another device/install or mismatched with the running revision fails closed — admission stays refused, never reopened on a guess. `recover-abort` is the only reopen path: it proves byte-unchanged external state, still-running exact original revision, owned drain and quiescence before advancing to `rolled_back`, releasing with the stored capability and expunging the record; a relay restarted in the activation gap owes no hold, so its `drain_not_held` status answer is accepted after the same revision and unchanged-state proofs — that proves the hold is gone, not that it was quiescent — and no release is owed; every failed proof leaves admission closed for manual recovery. Consequence: phases without consumers (quiescent, activating, verifying, committed and so on) wait for the issues that activate the stage, and a failed or incomplete activation state needs the operator's manual recovery instead of automatic retry.

## Failed activation rolls back to the exact journaled revision, automatically, with the barrier until it is proven

The transaction decision above left recovery of a `recovery_required` activation to the operator: automatic rollback did not yet exist, and the barrier's reopen path proved only a never-moved checkout. A failed activation that *did* move the source must not strand admission closed behind operator guesswork, and it must never roll back to a wrong tree. `rollback_transaction` (src/safe_update.py) therefore works only from the journal's exact prior commit — never a branch, main or a release tag — re-proves the hashed external references and the owned drain at that revision, and restores the prior commit object into the checkout only while `inspect_checkout` still accepts the working tree, so an intervening user edit or unsafe path mutation is a refusal, never an overwrite. The inspected service boundary is restarted only when the running relay does not already report the restored revision through the authenticated endpoint, so repeated recovery never repeats a service action; the barrier holds admission closed until the endpoint reports the exact prior revision, and only then is the journal finalized atomically to `rolled_back` (which removes the barrier) and the drain released with its own capability. Every failed proof keeps `recovery_required`, its barrier and an actionable remedy — nothing declares the rollback complete or reopens admission on a guess. `activate` runs the rollback automatically after an activation failure that has not already been finalized durably to `activated` — a barrier-refresh failure after that finalize leaves the standing activation and its record for `recover` to finish, never a rollback — and `safe_update recover <transaction-id>` finishes a rollback or, on an already finalized record, retries its pending cleanup: a rolled-back record first releases and proves its recorded drain and both terminal phases refresh the barrier (see the terminal rollback recovery decision below); terminal records are durable, bounded and secret-free (hashes and digests, never payloads). Consequence: `recover-abort` stays the path for a prepared transaction whose source never moved, `recover` is the path for a failed activation whose source may have, and both refuse anything but the recorded transaction of this install.

## A worker carries a role, and the role carries its instructions

A registry entry was a harness plus launch flags, so a reviewer and an implementer on the same model were identical to the relay and every review rule had to be retyped in the caller's task text. Roles are therefore declared in the registry (`description`, and `prompt` or `promptFile`, an optional `inputHeader`, and `delivery`), each agent names one with `role`, and the instructions are read once per load into the entry's private `_role` field. Two consequences follow. First, a role is never a request field: the owner of the registry decides what a worker is for, so a caller cannot reshape another owner's worker, and `POST /v1/tasks` gains nothing (the task record carries `role` and `rolePromptSha256` from the entry that dispatches it, and never the prompt text). Second, delivery is per adapter because the adapters differ in room: `prepend` puts the instructions in front of the input — the last `command` argument, or `task.input` of a `relay.adapter/v1` request — and `adapter` sends them as their own optional `role` field, which a `command` agent cannot receive, so it is a registry error there. A `command` agent's instructions share `AGENT_RELAY_MAX_COMMAND_INPUT_BYTES` with the input: a submission that would not fit is refused with `413 role_input_too_large`, and a queued task whose instructions grew while it waited fails at dispatch with the same code. `AGENT_RELAY_MAX_ROLE_PROMPT_BYTES` (default 32 KiB) bounds the instructions alone, and a relative `promptFile` resolves against the registry file's own directory so a registry and its prompts move together. Later work that adds an adapter must read the optional `role` field or lose adapter-delivered instructions; a reload replaces the instructions of queued tasks as well as new ones, as it already does for `options`, and a queued task whose reloaded entry lost its role, or whose instructions no longer fit, fails at dispatch with `role_removed` or `role_input_too_large` instead of running with other instructions or none.

## Terminal rollback recovery proves the live drain is gone

A rollback can finalize its durable record before releasing the live drain. Retrying only the disk-barrier refresh could then delete the sole recorded capability while admission stayed closed. Terminal rolled-back recovery now releases with the recorded revision and capability, tolerates an already absent hold, and requires status to report `drain_not_held` before refreshing the barrier and expunging the record. Every other status or transport result retains the record for an explicit retry; no service action is repeated.

## Workflow summary previews stay bounded and selectors are checked before waiting

A single-line output could fill a summary with the entire transcript, and an absent step selector could wait for the whole run before returning its existing error. Summary `firstLine` is now bounded to 200 characters including a trailing ellipsis on truncation, while `outputChars` retains the full size and the detail view retains the full text. A valid-shaped but absent step is rejected before a long poll. When both selectors are present, the step selector chooses the step and the summary selector chooses its shape; clamped MCP retries preserve both selectors.

## Service inspection validates the executable the manager launches

Finding the relay script anywhere in an argument list did not prove the service ran it: a wrapper could precede Python, and launchd could override the executable with `Program`. Inspection now accepts the script only at position zero or immediately after the validated Python interpreter. When launchd supplies `Program`, it must be absolute and exactly match the first program argument; conflicting definitions are refused rather than rewritten. Systemd inspection checks an absolute `XDG_CONFIG_HOME` and the installer's `~/.config` location, ignores relative XDG values, deduplicates candidates by their resolved location while preserving receipt paths, and refuses distinct definitions as ambiguous. This preserves existing installer output while accepting a configured unit location. Repeated systemd `Environment` directives are retained in order (an empty directive resets them), matching installer output, while other duplicate directives remain refused. Quoted assignments are parsed before checking for configuration inside the checkout. Existing direct service definitions and their bytes remain unchanged.

## No MCP call waits unless the caller asks for a wait

Collecting a result used to mean a blocking call: `wait_task` defaulted to a 60000 ms long-poll and `wait_workflow_events` to the same, and the initialize instructions presented `wait_task` as the step after every `delegate`. An orchestrator fanning out to several agents therefore parked its turn once per task even when it was not ready to read the result, and a call could sit long enough for a harness to move it to the background. MCP cannot push a result — one `tools/call` produces one response, and `serve` drops a message with no `id` — so a result must still be read back by a later call; what changed is that the read never waits unless it is asked to. `wait_task` and `wait_workflow_events` now return the current state at once when `maxWaitMs` is omitted, `delegate`, `run_workflow` and `resume_workflow` already waited only when given `waitMs`, and the instructions and tool descriptions describe submit, then read on your own schedule, with a wait named only as an explicit opt-in. The relay's HTTP `?waitMs=` long-poll is unchanged, and a supplied `maxWaitMs` keeps the existing clamping and `waitExpired` / `waitFailed` / `waitClamped` markers. Consequence: an orchestrator pays a round trip per read instead of one parked call, so a caller that wants the result now must pass a wait to get it.

## The update check runs when the session loads, and the last attempt is a record, not a log line

Claude Code checks for updates on startup and periodically while running, keeps the result of the last attempt somewhere `claude doctor` can report it, and applies an update without disturbing running work. agent-relay had only part of that pattern: a timer firing every six hours into an append-only log. A device that stayed up between firings never checked when its session loaded, and a deferred restart or a failed pull was visible only by reading the log file. The launchd unit now sets `RunAtLoad` true (the systemd timer already had `OnBootSec`), so a check runs when the session loads as well as on the interval, and `scripts/update.sh` records every attempt — outcome, the commits it moved between, and whether a restart is still pending — in `.git/agent-relay-update-status.json`, beside the pending-restart marker the script already kept there and renamed into place so a reader never sees a half-written record. `GET /healthz` reads it on each request and reports it as `update`, `null` when the script has never run for that install; only the known keys pass through, and an unreadable, oversized or symlinked file reports as no attempt rather than failing a health check. Consequence: an owner who installed before this change must rerun `scripts/install-service.sh` to regenerate the update timer, because a check cannot reach a unit already on disk; and the timer stays metadata-only — it runs the release checker and never pulls source or restarts the relay, so installing source automatically remains the separate work of the activation design.

## A running MCP server says when the install changed under it, and never restarts itself

The relay updates on a timer and restarts its own service, but the MCP server belongs to the client that spawned it: Claude Code and Codex hold it for the life of a session and nothing in the update path touches it. An update could therefore leave a client serving tool definitions and instructions from an older commit with no signal at all — which is how a session can keep the behaviour of a commit that merged hours earlier. At import the process records the modification times of the source files it actually imported from its own directory, plus the checkout's short HEAD read from `.git` itself (never by running git: an MCP process must not trust a git found on PATH, the same refusal the relay makes for itself, and a linked worktree's `gitdir:` and `commondir` indirections are followed, since HEAD lives in the worktree's own directory and the ref it names in the common one). At `initialize` it re-stats those files, and when any differs the `instructions` gain one sentence naming the checkout's current commit and the one this server loaded, asking the client to restart the MCP server — a new session or an MCP reconnect. Only imported files are watched: `server.py` changing cannot make the MCP server stale, so it must not nag. Consequence: the notice is text in `instructions`, never a tool result and never a claim that anything was restarted, because the server cannot restart itself and does not try — the client owns that process and the relay takes its own code on its next restart; the comparison is a stat of a handful of files rather than a content read on every `initialize`, so a false positive costs one needless restart instead of a per-call scan, and the fresh-start instruction-length bound stays at 1024 while only the test that produces a stale notice asserts 1536, because the notice is conditional and bounded.

## Systemd environment inspection preserves logical directives

The repeated-Environment scan previously discarded values accepted by configparser through DEFAULT inheritance or a colon delimiter, and treated continued directives as unrelated physical lines. Inspection now refuses those unsupported environment forms explicitly and folds backslash continuations (skipping comment lines) before classification. Canonical `[Service]` `Environment=` assignments retain order, reset behavior and the internal-checkout check; service definition bytes are never rewritten. An unfinished continuation or an empty physical line while a continuation is pending refuses with a diagnostic naming the cause, so text cannot be folded across an empty physical line. Comment-only lines instead remain ignored within a pending continuation: following text, even one starting with `ExecStartPre=`, belongs to the same environment value rather than a separate service directive. Forbidden directives outside a continuation are still refused.

## Fresh instructions keep their original bound and invalid commit metadata stays unknown

This supersedes the instruction-bound, commit-validity and sentence-count portions of "A running MCP server says when the install changed under it, and never restarts itself". Fresh initialization keeps the original 1024-character test bound; only a stale notice uses the separate 1536-character bound. A commit read from detached HEAD, a loose ref or packed refs must contain 7–40 lowercase hexadecimal characters before its first seven characters can appear in the notice; empty, short or malformed metadata reports unknown. Consequence: local metadata remains the only source, git is never executed by the MCP server, and an invalid identifier cannot masquerade as a checkout commit in a restart notice. The notice is short bounded text, not a fixed sentence count.

## The local commit reader supports full SHA-256 IDs too

This supersedes the 40-character ceiling in "Fresh instructions keep their original bound and invalid commit metadata stays unknown". The reader accepts the existing 7–40 lowercase-hex form or a full 64-character lowercase-hex SHA-256 ID, displaying the first seven characters in either case. Lengths 41–63 remain refused deliberately: they are neither the existing short/SHA-1 form nor a full SHA-256 ID. Consequence: real SHA-256 loose, packed and detached checkouts retain their notices without widening acceptance to malformed intermediate-length metadata; git is still never executed by the MCP reader.

## needsPolicy changes admission, not the run outcome

A fan-in may tolerate a failed branch without making the run successful. `any` requires a nonempty `needs` list, waits for all needs to become terminal and at least one to complete, and renders status/error markers for non-completed terminal ancestors. Unfinished ancestors remain empty; `all` keeps non-completed terminal ancestors empty too. Failed or skipped branches still fail the run, while cancellation still cancels it. Step views retain the submitted policy (`null` when omitted), and journals predating `needsPolicy` resume with `all` behavior. Consequence: clients must distinguish the fan-in step's success from the whole run's outcome and must not infer live scheduler state from an unfinished ancestor's template output.

## The installer writes one command and `info` answers the four facts

Every doc command was written as an absolute path into the checkout because the install left no command on `PATH`. The installer now writes one wrapper into the per-user bin directory that execs the checkout's `src/cli.py` with the validated interpreter, so `agent-relay` follows the checkout that runs the service rather than a second installed copy of the code. The CLI keeps only person-facing answers (`info`: relay URL, artifact release page, token path, checkout) and imports `server` for the token path. The installer bakes the port it installed with into the wrapper (`AGENT_RELAY_PORT`), so `info` reports the port the service listens on rather than the invoking shell's default; `AGENT_RELAY_URL`/`A2A_RELAY_URL` remain the explicit override. The wrapper carries a marker, and `--uninstall` removes only that wrapper, leaving a foreign file at the same path. Because `~/.local/bin` is not on the default macOS login PATH, the installer prints the line to add instead of claiming the command is already resolvable. Consequence: docs can name `agent-relay` for install and status once that directory is on PATH, and any new person-facing fact belongs in `info`, not in a new wrapper.

## Malformed text is refused before a codec can turn it into a 500

`POST /v1/tasks` measured `input` in bytes and resolved `cwd` with `os.path.realpath`, and both encode the caller's string. A JSON escape such as `"\ud800"` decodes to a lone surrogate, and a NUL in `cwd` makes `realpath` raise, so either reached the handler's blanket `except Exception` and answered `500 request_failed`. The input check now refuses text that is not UTF-8 as `400 invalid_input`, and the cwd resolver refuses a NUL or an unencodable path as `400 invalid_cwd` before `realpath` sees it. Consequence: the documented 400 contract holds for input that cannot be encoded, and no task is created for it.

## Every write to a live task dict holds LOCK

A task's dict is read for every listing, single-task read, long poll, replay, submission answer and cancellation (`visible()`), and it is written from the worker side as the task starts and finishes: `_drain` stamps `_extra_args`, `_sandbox`, `_adapter`, `startedAt` and the deadline, `_spawn` records `_proc`, and `_finish`/`_release`/`cancel_task` add or remove the terminal fields. Rendering outside the lock meant a poll that overlapped a start or a finish raised `RuntimeError: dictionary changed size during iteration` and answered `500 request_failed` (#334), and the same class of bug came back when the worker thread stamped `_deadline` after `_drain` had already published the running task. The relay therefore holds one rule: a write to a task dict that `TASKS` holds is performed while `LOCK` is held — the dispatch fields are stamped before the worker thread exists, and `visible()` builds its whole snapshot inside the lock (`LOCK` is reentrant, so a caller that already holds it stays correct). Consequence: a new task field must be written under `LOCK`, or set before the task is published to `TASKS`, and no reader may render a task dict outside it; a worker-side insert outside the lock is a bug even when the window looks too small to hit.

## A resume takes the same stored-run slot as a submission

`A2A_RELAY_MAX_WORKFLOWS` bounded the store only for submissions: `resume` inserted a run into `self._workflows` and started its executor unconditionally, so any journaled id could add a run and a thread without limit. Because evicting a run leaves its journal behind, every evicted id stayed resumable, and resuming many distinct ids bypassed the documented bound. A resume now asks `_make_room` under the same lock that guards admission, and only when the id is not already stored: a run still stored and finished is resumed in place over its own entry, so asking for room there would evict an unrelated finished run and release its `requestId` for nothing — the at-least-once bug #327 records. A journal-only id takes a slot by the submission rule and is refused with `503 workflow_capacity_reached` when the store is at the bound and holds no finished run; the refusal creates no run, no journal record and no executor. Consequence: operators sizing `A2A_RELAY_MAX_WORKFLOWS` must account for resumes as stored runs, and a client resuming a journal-only id while the store is full of unfinished runs must retry after one finishes.

## The trusted git allowlist names each platform's own installation

The allowlist was `/usr/bin/git` and `/bin/git` on every host, so on Windows the relay found no git and reported `revision` as `unknown` even inside a real checkout — while still refusing to search `PATH`, which is the protection the allowlist exists for. The list is now chosen by platform: the POSIX system paths, or the machine-wide Git for Windows `cmd` executable under `ProgramFiles` on Windows. A per-user install under `LOCALAPPDATA` is deliberately not a candidate: it sits in the relay user's own profile, which a task can write, so a planted git there would run unsandboxed at the next relay start — exactly what the allowlist prevents. An unset `ProgramFiles` leaves no Windows candidate. Consequence: Windows reports a real revision from a standard machine-wide Git for Windows install; a per-user or otherwise non-standard install still needs `AGENT_RELAY_GIT`, and no path is ever looked up in `PATH`.
