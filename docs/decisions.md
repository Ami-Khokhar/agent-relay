# Decisions

## Release discovery is metadata-only

The project has no published releases or tags yet, and its existing updater pulls and restarts source checkouts. Release discovery therefore uses the canonical GitHub HTTPS API with a bounded response and never installs or executes fetched content. Stable releases are the default, prereleases require an explicit option, and no release is a normal result. Later installation work must establish immutable content verification and a separate user consent step.

## Scheduled checks only offer release metadata

The timer may fetch bounded canonical release metadata, but it must not update installed code or restart the relay. It writes a private, validated offer without marking it offered; MCP initialization reads only that local cache and offers a version notice to the client once per version, while release notes remain available only from an explicit `check_updates` call. This records delivery to the client, not proof that a human read it. The updater script stays a separate manual source-checkout operation until an activation and consent design is ready. Owners must rerun the installer to replace timer definitions installed by an older version.

## The release notice cache serializes whole transactions behind a private sibling lock

The device-local notice cache has two writers — the scheduled timer's refresh and MCP initialization's `cached_notice` — and each one is a read/decision/write sequence: read the cache, decide whether this version was already delivered, write the outcome. Unserialized, two concurrent clients can both decide a version is undelivered and both deliver it, and a timer refresh replacing the file between a client's read and write can erase delivery history and redeliver the same version. The cache file itself cannot carry the lock, because every write atomically replaces it and a lock on the old inode would not follow the replacement. Every transaction therefore runs under an exclusive `flock` on a stable sibling file (`release-notices.lock`), with the same private regular-file checks as the cache (no symlink, owned by this user, mode 0600 on POSIX); nested entry — the write inside `cached_notice`'s own transaction — reuses the held lock instead of re-acquiring, so a transaction cannot deadlock itself. Lock acquisition is bounded by a timeout, and a failure raises an actionable error: a caller never claims a notice was delivered when the transaction could not run. `_write_cache` without an explicit `notified_version` preserves the previous `notifiedVersion`, and both `cached_notice` and `_notify_once` deduplicate on that one field, so a refresh updates the offer without redelivering a version already shown. A separate consequence of round-tripping offers through the cache: the read cap must cover the worst-case JSON escaping of a maximum-size offer (2000 astral characters serialize as up to 12 characters each), so the cap is 32 KiB rather than 16 KiB, still a bound. On non-POSIX platforms there is no `flock`: the policy is explicit — transactions are not cross-process serialized there, writes stay atomic-by-replacement, and the project's supported notice-cache platforms are POSIX.

## A foreach step matches fail patterns per item

`failIfOutputMatches` used to be tested against the step's aggregated output, which for a `foreach` step is a JSON array of the item outputs. An anchored pattern then either could not see what an agent reported (`^BLOCKED` never matches a report quoted inside the array) or fired on the serialization itself (`^\[` failed every healthy fan-out). The pattern is now tested against each completed task's own raw output, before the step may complete: one matching item fails the whole step with `output_matched_fail_pattern` and its dependents are skipped, and the step still keeps the JSON array as its output for a caller to inspect. Consequence: matching is per item, so an aggregate-shaped pattern (`^\[`) no longer has a meaning on a `foreach` step, while the other terminal causes keep their precedence — a task that failed, timed out or was cancelled still decides the step before the pattern is read, and `retries`, `repeat` and journals written before the field existed behave exactly as before.

## Tests never read or consume the device notice cache

MCP initialization reads the device-local notice cache and marks a delivered version, so any test that starts an MCP server process — or calls an in-process initialize handler — against the real environment would consume and rewrite the developer's own notice state, and its assertions would depend on whatever cache and installed version the machine happens to have. Every test MCP process therefore gets a private `XDG_CACHE_HOME`: `McpClient` defaults to a temporary cache it removes in `close()` (a caller-supplied cache is honored and left to the caller), in-process initialize handlers run under a fixture that points `XDG_CACHE_HOME` at a temporary directory, and any other direct `mcp_server.py` spawn must do the same. Tests that seed a notice cache derive the offered version relative to the installed baseline, and scheduled-refresh coverage passes an explicit installed baseline to `cache_latest_offer`, so a version bump in `pyproject.toml` cannot silently invalidate them. Consequence: a new test that spawns the MCP server without a private cache is a regression, and release-offer fixtures must outrank the declared version rather than assume one.

## The release-check timer's units carry no relay environment

`A2A_RELAY_PORT` and `AGENT_RELAY_DIR` used to be set in the update timer's launchd and systemd units alongside the checker's own `ExecStart`. The check is metadata-only: `release_discovery.py --cache-offer` locates the checkout from itself, reads its state from the private device cache, and never talks to the relay, so those variables described a coupling that did not exist; a future reader could also mistake the timer for one that manages the service. The checker units now set only `PATH`, while the relay service's units keep the port and the working directory as before, and the installer's messages and README quickstart describe the timer as a release check. Consequence: the timer keeps its historical unit names (`agent-relay-update.*`, `com.agent-relay.update`) and flags, the relay's configuration is untouched, and tests parse the generated plist with `plistlib` and the systemd sections rather than matching strings, so the environment split is asserted structurally on both service managers.

## Release identity is resolved from canonical tag refs and consent is a private device-local record

The stable-update work needs more than discovery's "a newer version exists": the exact release an operator considers installing must be bound to an immutable commit before any content is trusted. `release_identity.resolve_release` therefore ignores `target_commitish` — which moves and is never proof — and resolves the tag through the bounded canonical `git/ref/tags` API, peeling an annotated tag once through `git/tags`, to a 40-hex commit. Only `Ami-Khokhar/agent-relay` counts, only stable published releases, HTML URL must be canonical, and every strict-JSON parse rejects duplicate keys; absent assets or no release at all are clear refusals, and nothing is ever created on the operator's behalf. The release publishes an `agent-relay-manifest.json` asset (`agent-relay.update/v1`) whose exact fetched bytes are hashed into the identity and whose inventory of tracked path/mode/SHA256 entries is validated strictly; the hash authenticates content only because canonical GitHub maintainers publish it over HTTPS — it is not independent signing, and no signing scheme is claimed.

Approval is its own step and never degenerates into a yes flag or an environment variable: `approve` requires a real TTY and the operator typing the exact version and the full commit, then records under a cross-process lock a private 0600 consent bound to the canonical installation realpath, a locally generated device id, the full identity digest, a fresh nonce, and at most a 15-minute expiry. `consume_consent` re-checks everything — expired, future, replayed, mutated, wrong-device and changed-path consent are all refused — and burns the record atomically. Discovery, scheduled notices and `inspect` remain metadata-only, and the safe-update CLI never runs git, install or service commands; the activation that will consume the consent is deliberately left for later stages of the same CLI.

## The update drain is a server-held shared lock with an opaque, transaction-bound capability

Activating a staged release must not race new admissions: an updater that quiesces by reading `/healthz` can still restart in the same instant a task is accepted. The relay therefore holds the quiescence state itself. `POST /v1/admin/update/drain` acquires it once for one transaction, bound to the exact commit the relay reports (`healthz` `revision.commit`, refused when unknown), and returns an opaque 64-hex capability the relay minted; the refusals that close admission (`GET` status composes the verdict from the same counts) are the server's, never the client's. A held drain refuses every new external admission — tasks, workflow submissions and resumes — under the server lock, so a submission and an acquire are one atomic decision, and a replayed `requestId` keeps its prior answer instead of a refusal; already accepted workflows keep reaching their child tasks only through a module-level internal admission path bound to the engine at startup, never through a caller-set request field. Quiescence counts active adapter slots (including cancelled adapters still running), queued accepted tasks, and every nonterminal workflow once — a run in a step gap, a retry delay or awaiting fanout is still work that may create tasks. `GET` status answers only the holder's exact transaction, revision and capability (constant-time compared); malformed fields, wrong revisions, foreign capabilities and even a free drain are errors, never `idle`, and status never hands out a new token. There is no expiry during activation: admission reopens through the explicit `DELETE` release with the same capability (or a future durable recovery path). `safe_update.py drain` is the rehearsal consumer: it verifies the staged receipt and the consumed approval consent, holds the drain, waits a bounded time for the server's own quiescence acknowledgement, prints the result and releases; it calls no service control. The hold lives in server memory, so a relay restart reopens admission — that is a durable-recovery concern for the activation stage, not a silent expiry.
